# 构建说明

## 硬件

保持原环境：Vivado2018.3＋JFM kit5.3.1.8；位流经Procise2025.1.1 temp针对JFMQL30TAI676H转换。XPR器件设置xc7z030ffg676-2属于现有厂商流程。

在Vivado2018.3打开`01_hardware/project/ps_in.xpr`。顶层ai7030_top，外部IP已放入`01_hardware/ip_repo/`。本包保留IP输出和封装容器，使用上述版本及厂商流程构建。

只检查工程文件：

```powershell
& 'D:/Vivado/2018.3/bin/vivado.bat' -mode batch -source '01_hardware/scripts/verify_project.tcl'
```

检查结果输出到05_validation/packaging，生成的recreate_project.tcl用于恢复工程定义。该操作检查工程文件及引用；硬件综合使用下一节的构建入口。

从工程根目录执行以下命令构建硬件：

```powershell
& 'D:/Vivado/2018.3/bin/vivado.bat' -mode batch -source '01_hardware/scripts/rebuild_hardware.tcl'
```

该入口配置128KiB FIFO，并依次执行综合、布局布线和报告导出，结果写入01_hardware/build_results；启动构建会重置指定运行。构建环境需要安装厂商JFM补丁和Procise。当前版本的资源、时序及DRC报告位于05_validation/hardware。构建脚本将新检查点写入01_hardware/build_results；既有routed.dcp在完整交付目录留档。

硬件构建到BOOT的完整顺序：Vivado原始bit → Procise disable_icap转换 → 使用FSBL、bl31、U-Boot及BIF打包。04_firmware/an5641_dma_fix.bif保留原工具路径，重新打包时改为该目录实际文件位置；已有04_firmware/BOOT.bin用于对应当前实测版本。

## 板端C++

源目录：02_board_app/source/runtime；C++17、CMake3.16以上、AArch64交叉编译器、iCraft3.36.1和既有厂商第三方静态库。CMake使用FPAI_DEPS_DIR/thirdparty，iCraft通过CMAKE_PREFIX_PATH寻找。

在已配置AArch64工具链的Linux/WSL中，从本包根目录执行：

```bash
cmake -S 02_board_app/source/runtime -B build/board \
  -DCMAKE_TOOLCHAIN_FILE=/path/to/aarch64-toolchain.cmake \
  -DFPAI_DEPS_DIR=/path/to/fmql_assets/deps \
  -DCMAKE_PREFIX_PATH=/path/to/icraft/cmake
cmake --build build/board --target yolo_qwen_esp32_hdmi -j2
```

工具链示例见tools/aarch64-toolchain.cmake.example，路径由使用者填写。编译得到的程序放入板端runtime/yolo_qwen_esp32_hdmi；包内已附当前运行二进制和模型。

第三方依赖目录应包含原工程需要的OpenCV、FFmpeg、JPEG、YAML、SSL、Eigen及iCraft库；CMake保留既有链接顺序。包内vendor为源代码依赖，SDK二进制库由开发环境提供。

## Python与动作模型

板端按原Python3.8/aarch64环境：`python3 action/install_deps.py`将wheelhouse内NumPy1.24.4和ONNX Runtime1.19.2安装到action/python私有目录。PC端需要Python及Pillow，ESP传输使用随包提供的USB封装/原部署依赖。

独立算子实验使用各自工具版本、脚本、参考向量和启动镜像，详见06_operator_experiments/README.md；当前演示使用04_firmware中的BOOT。
